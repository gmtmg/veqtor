Claude Code Auto Mode 完全ガイド ― 許可プロンプトをAIが自動判定する新しい使い方

⏱ 10分で学べること
  • Auto Modeとは何か、既存の許可モードとの違い
  • 分類器が安全/危険を判定する仕組み
  • 有効化の手順と利用条件
  • 組織向け環境設定（environment / allow / deny）
  • 実践的な設定例とトラブルシューティング

「許可しますか？」を減らす、新しい選択肢

Claude Codeを使っていると、ファイルの編集やコマンドの実行のたびに「許可しますか？」と聞かれます。安全のために大事なステップですが、信頼できる作業が続くと煩わしく感じることもあります。

これまでの選択肢は2つでした。

  • 毎回手動で許可する（安全だが中断が多い）
  • --dangerously-skip-permissions（中断ゼロだが安全チェックも全スキップ）

Auto Modeはこの間を埋める第3の選択肢です。別の分類器モデルが各操作を事前に審査し、安全な操作は中断なしで実行、危険な操作だけをブロックします。

Claude Codeの許可モード一覧

Auto Modeを理解するために、Claude Codeが提供する全6モードを整理します。

モード 許可なしで実行できる操作 向いている場面
default 読み取りのみ 初期設定、慎重な作業
acceptEdits 読み取り + ファイル編集 + 基本コマンド コードを書きながらレビュー
plan 読み取りのみ（編集は計画のみ） 方針を固めてから着手
auto 全操作（分類器が背後で安全チェック） 長時間タスク、許可疲れの解消
dontAsk 事前許可されたツールのみ CI/スクリプト
bypassPermissions すべて（安全チェックなし） コンテナ・VM内のみ

autoは「全部通す」のではなく、「分類器に委ねる」モードです。bypassPermissionsとの決定的な違いは、不審な操作をブロックする仕組みが常に動いている点にあります。

Auto Modeの仕組み

分類器の判定フロー

Claudeがツールを呼び出すたびに、以下の順序で判定が行われます。

  1. 許可/拒否ルールの確認 — ユーザーが設定したallow/denyルールに一致すれば即決
  2. 読み取り専用・ファイル編集の確認 — 作業ディレクトリ内の読み取りや編集は自動承認（保護パスを除く）
  3. 分類器に送信 — 上記に該当しないものは分類器モデルが審査
  4. ブロック時の代替 — 拒否された場合、Claudeは理由を受け取り別のアプローチを試みる

分類器はユーザーのメッセージ、ツール呼び出し、CLAUDE.mdの内容を参照します。ツールの実行結果（出力内容）は参照しません。これにより、ファイルやWebページに埋め込まれた悪意あるプロンプトによる分類器の操作を防いでいます。

デフォルトでブロックされる操作

分類器は作業ディレクトリとリポジトリのリモートだけを信頼します。それ以外は「外部」として扱われます。

  • curl | bash のようなダウンロード＆実行
  • 外部エンドポイントへの機密データ送信
  • 本番環境へのデプロイ・マイグレーション
  • クラウドストレージの大量削除
  • IAMやリポジトリ権限の変更
  • 共有インフラの変更
  • セッション前から存在するファイルの不可逆的な破壊
  • force push、mainブランチへの直接push

デフォルトで許可される操作

  • 作業ディレクトリ内のファイル操作
  • ロックファイル/マニフェストに記載された依存パッケージのインストール
  • .envの読み取りと、対応するAPIへの認証情報送信
  • 読み取り専用のHTTPリクエスト
  • 作業開始時のブランチ、またはClaude自身が作成したブランチへのpush

利用条件

Auto Modeはすべてのユーザーが使えるわけではありません。以下の条件すべてを満たす必要があります。

条件 詳細
バージョン Claude Code v2.1.83以降
プラン Max、Team、Enterprise、またはAPI（Proは不可）
モデル Sonnet 4.6、Opus 4.6、Opus 4.7（Maxプランの場合はOpus 4.7のみ）
プロバイダ Anthropic APIのみ（Bedrock、Vertex、Foundryは不可）
管理者設定 TeamおよびEnterpriseでは管理者が事前に有効化する必要あり

Auto Modeの有効化

セッション中の切り替え

CLIではShift+Tabを押すとモードが順に切り替わります。

default → acceptEdits → plan → auto

初回選択時にオプトインの確認が表示されます。「No, don't ask again」を選ぶとサイクルからautoが外れます。

起動時に指定

claude --permission-mode auto

デフォルトに設定

.claude/settings.jsonに以下を追加すると、常にAuto Modeで起動します。

{
  "permissions": {
    "defaultMode": "auto"
  }
}

VS Codeの場合

プロンプト入力欄の下部にあるモードインジケーターをクリックし、「Auto mode」を選択します。事前に拡張設定で「Allow dangerously skip permissions」を有効にしておく必要があります。

組織の環境を定義する ― autoMode.environment

Auto Modeの一番重要な設定項目です。分類器に「どのリポジトリ、ドメイン、クラウドバケットが自組織のものか」を教えることで、誤ブロックを減らせます。

未設定のままだと、作業ディレクトリと設定済みリモート以外はすべて「外部」と見なされます。社内のGitHub orgにpushしようとしてもブロックされることがあります。

{
  "autoMode": {
    "environment": [
      "$defaults",
      "Organization: Acme Corp. Primary use: software development",
      "Source control: github.example.com/acme-corp and all repos under it",
      "Trusted cloud buckets: s3://acme-build-artifacts, gs://acme-ml-datasets",
      "Trusted internal domains: *.corp.example.com, api.internal.example.com",
      "Key internal services: Jenkins at ci.example.com, Artifactory at artifacts.example.com"
    ]
  }
}

ポイントは3つです。

  • "$defaults"を必ず含める。省略すると組み込みの環境定義がすべて消えます
  • 正規表現ではなく自然言語で書く。分類器は人間が読むように解釈します
  • 段階的に追加でOK。まずソースコントロールと主要サービスだけ設定し、ブロックが出たら足していく運用が推奨されています

ルールのカスタマイズ ― allow / soft_deny / hard_deny

分類器の判定ルールは3層構造で、上書きできます。

フィールド 動作 ユーザーの明示的意図で上書き
hard_deny 無条件でブロック 不可
soft_deny ブロック（デフォルト） 可能（allowルールまたは会話中の明示的指示で）
allow soft_denyの例外として許可 —

優先順位は hard_deny > soft_deny > allow > ユーザーの明示的意図 の順です。

設定例

{
  "autoMode": {
    "environment": [
      "$defaults",
      "Source control: github.example.com/acme-corp"
    ],
    "allow": [
      "$defaults",
      "Deploying to the staging namespace is allowed: staging is isolated and resets nightly",
      "Writing to s3://acme-scratch/ is allowed: ephemeral bucket with 7-day lifecycle"
    ],
    "soft_deny": [
      "$defaults",
      "Never run database migrations outside the migrations CLI",
      "Never modify files under infra/terraform/prod/"
    ],
    "hard_deny": [
      "$defaults",
      "Never send repository contents to third-party code-review APIs"
    ]
  }
}

各セクションで"$defaults"を含めることが重要です。省略するとそのセクションの組み込みルールがすべて置き換わります。例えばsoft_denyから$defaultsを外すと、force pushやcurl | bashのブロックルールも消えます。

会話中にルールを伝える

設定ファイルだけでなく、会話の中で境界を伝えることもできます。

pushしないで
デプロイ前にレビューさせて

分類器はこれらの発言を「ブロックシグナル」として認識し、デフォルトルールでは許可される操作でもブロックします。この境界は、あなたが後のメッセージで解除するまで有効です。

注意点: 境界はルールとして保存されるのではなく、分類器が会話履歴から読み取ります。コンテキスト圧縮で該当メッセージが消えると、境界も失われる可能性があります。確実に守らせたい場合はpermissions.denyルールを設定してください。

ブロック時の挙動とフォールバック

ブロックされた操作は通知として表示され、/permissionsの「Recently denied」タブに記録されます。そこでrキーを押すと手動で再試行できます。

自動フォールバック

  • 連続3回ブロックされると、Auto Modeが一時停止し通常の許可プロンプトに戻る
  • 累計20回ブロックされた場合も同様に一時停止
  • 手動で操作を承認すると、Auto Modeが再開する
  • 許可された操作が間に入ると連続カウンタはリセットされる

繰り返しブロックされる場合は、分類器にインフラの情報が不足しているサインです。autoMode.environmentに該当の宛先を追加してください。

設定の検証コマンド

3つのCLIサブコマンドで、設定の確認と検証ができます。

# 組み込みのデフォルトルールを表示
claude auto-mode defaults

# $defaults を展開した実効設定を表示
claude auto-mode config

# カスタムルールへのAIフィードバック（曖昧・冗長・誤検知リスクを指摘）
claude auto-mode critique

設定を変更したらclaude auto-mode configで実効ルールが意図通りか確認する習慣をつけましょう。

サブエージェントでのAuto Mode

Auto Modeはサブエージェントにも適用されます。3つのタイミングでチェックが行われます。

  1. 起動前 — タスクの内容が危険に見える場合、起動時点でブロック
  2. 実行中 — 親セッションと同じルールで各操作を審査（サブエージェントのfrontmatterでpermissionModeを指定しても無視される）
  3. 完了後 — サブエージェントのアクション履歴全体を分類器がレビュー。問題があればセキュリティ警告が結果に付加される

保護パス ― Auto Modeでも守られるファイル

bypassPermissions以外の全モードで、以下のパスへの書き込みは自動承認されません。Auto Modeでは分類器による審査を経由します。

  • ディレクトリ: .git、.vscode、.idea、.husky、.claude（ただし.claude/commands、.claude/agents、.claude/skills、.claude/worktreesは除く）
  • ファイル: .gitconfig、.gitmodules、.bashrc、.zshrc、.profile、.mcp.json、.claude.json など

実践シナリオ：こんなときどうなる？

シナリオ1: 普段の開発作業

作業ディレクトリ内でのファイル編集、npm testの実行、自分のブランチへのpush。これらはすべて自動承認されます。体験としてはbypassPermissionsとほぼ同じですが、安全ネットが効いている状態です。

シナリオ2: curl | bash が含まれるコマンド

インストールスクリプトの実行など。ブロックされます。Claudeは代わりにファイルをダウンロードしてから実行する、あるいは手動での確認を促す別のアプローチを試みます。

シナリオ3: mainブランチへのforce push

hard_deny相当の操作です。無条件でブロックされます。ユーザーが「force pushして」と言っても、分類器が阻止します。

シナリオ4: 社内GitHub orgへのpush（environmentで定義済み）

autoMode.environmentにソースコントロールを定義してあれば、自動承認されます。定義していなければブロックされます。

コストとレイテンシ

  • 分類器はサーバー側のモデルで動作し、/modelの選択とは独立
  • 分類器の呼び出しはトークン使用量にカウントされる
  • 各チェックでは会話の一部と保留中のアクションが送信されるため、実行前に1往復のオーバーヘッドが発生
  • 読み取り操作と作業ディレクトリ内のファイル編集は分類器をスキップするため、オーバーヘッドなし

まとめ

  1. Auto Mode = 「分類器に許可判定を委ねる」モード。全スキップでも毎回確認でもない中間地点
  2. Shift+Tabで切り替え、またはsettings.jsonでデフォルト化
  3. 利用条件あり: Max/Team/Enterprise/APIプラン、対応モデル、Anthropic APIのみ
  4. autoMode.environmentが最重要設定。組織のインフラを自然言語で伝える
  5. $defaultsを忘れずに。省略すると組み込みルールが消える
  6. 繰り返しブロックされたら、environmentに宛先を追加するサイン
  7. リサーチプレビュー段階。今後の変更の可能性あり
Compass

Auto Modeは「もう--dangerously-skip-permissionsしか選択肢がないんだよな…」と感じていた方には朗報です。まずはデフォルト設定のままShift+Tabで試してみて、ブロックが気になったらenvironmentを足していく、という段階的なアプローチがおすすめです。
